# Adversarial verification boundary

Q3 divides verification by the code that owns each concurrency invariant. It
does not treat a framework-wide tool count as evidence and does not reproduce
neighboring implementations inside bombay.

| Owner | Verified adversarial surface | Evidence boundary |
|---|---|---|
| Bombay Behavior local `63045b4` (post-0.10) | Definition/active typestate, fold/action ordering, named typed send selection, affine nested delegation, nominal behaviors, creation and replacement resolution, supervision, FSM, stashing, receive timeout | Pure exhaustive/property/fuzz models in the Behavior testkit; no shared runtime state exists to Loom-model |
| Bombay Communication 0.1.1 | Two-lane priority, bounded FIFO, backpressure wakeup, cancellation, closure, and payload fate | Communication-owned implementation Loom models plus property and teardown suites |
| Bombay Transition 0.1.0 + Machine Executor 0.1.0 | Affine `Machine::step`, exclusive turn poison, successor installation, and rejected-input ownership | Owner tests plus bombay engine production-path and inversion oracles |
| Bombay Observe 0.1.0 | Exact-generation publication, registration/waker races, cancellation, pooling, and panic safety | Observe-owned implementation Loom, exhaustive, stress, and fuzz suites |
| Bombay Timers 0.1.0 | Key/generation replacement, deadline order, and single expiration | Timers-owned Loom plus differential, exhaustive, and fuzz suites |
| Bombay Address 0.1.1 | Concurrent claim/resolve/release, generation isolation, reclamation, and reentrancy | Address-owned implementation Loom, state-machine, stress, Miri, and fuzz suites |
| bombay | Tokio task completion composed with mailbox closure, registration retirement, observation publication, lifecycle facts, and address reuse | Real-executor race, generated operation sequences, shared libFuzzer target, and supported Miri smoke path in this repository |

The locked Bombay crate implementation and test trees match their current
local sibling crate trees at the commits recorded in the Q3 ledger audit.
Bombay therefore consumes those proofs at the exact versions it composes.
It does not run sibling repository gates from its own CI and does not claim
their implementation coverage as bombay coverage.

## Bombay gates

The deterministic property suite is part of the ordinary workspace test gate:

```console
cargo test --workspace
```

It converts generated byte vectors into unique payload permutations. Producers
race through a capacity-one mailbox; every accepted payload must reach the pure
behavior exactly once, normal completion must be published, and the logical
address must then accept a fresh generation. The multithreaded oracle races a
typed graceful-shutdown request with abort for 64 pairs of incarnations. Each
incarnation must publish one ordered `Prepared -> ... -> Retired -> Completed`
sequence and reuse must carry a distinct registration identity.

The fuzz target imports that same payload/reuse oracle rather than maintaining
a weaker parallel model:

```console
nix develop .#fuzz
cd crates/bombay/fuzz
cargo fuzz run runtime_operations -- -runs=256
```

The supported Miri lane is deliberately deterministic and single-threaded:

```console
nix develop .#miri
cargo miri setup
MIRIFLAGS="-Zmiri-many-seeds=0..8" \
  cargo miri test -p bombay-rs --test adversarial_oracle \
  miri_supported_payload_and_reuse_composition
```

Miri checks bombay's public payload-delivery, terminal-publication, and
address-reuse composition. It does not establish Tokio scheduler correctness,
and the multithreaded race makes no Miri claim.

## Why bombay has no Loom copy

The bombay-owned race crosses Tokio task scheduling and five separately
owned crates. Tokio is not replaced by a Loom implementation here, and the
locked Bombay crates select their own Loom synchronization under `cfg(loom)`.
A local abstract copy would test different code, duplicate their primitive
models, and recreate the synthetic lifecycle proof objects removed by D2.
Consequently, primitive linearization is Loom-checked by its owning crate and
bombay checks the real composed temporal outcome under Tokio.

The inversion oracles are direct: dropping or duplicating an accepted payload
prevents normal completion or raises the behavior error; publishing completion
before registration retirement makes immediate reuse fail; duplicating or
reordering lifecycle terminal facts fails the per-incarnation sequence; and
aliasing a replacement identity fails the distinct-generation assertion.
