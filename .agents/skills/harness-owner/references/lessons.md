# Lessons for the next harness

Joel plans a harness in Rust that works for any project. This file collects what
the Labcast harness taught, as requirements that do not depend on Labcast. Each
row names what a harness must do, what happened when this one did not, and
where the evidence is. Add a row when a problem of a new kind is solved. Do not
add a row without a measured incident.

## Processes and tests

| A harness must | What happened | Evidence |
| --- | --- | --- |
| Signal a process only through a reference that cannot be reused: a child that it has not yet waited for, or a process handle of the system (on Linux a pidfd). A stored number checked against its start time narrows the risk and does not remove it, because the number can change hands between the check and the signal. | Tests stored process numbers and signalled them minutes later. Under load the machine gave out all 99,999 numbers in 192 seconds, and a test of another session got SIGKILL. | #590; the pull request "Signal only own processes in the harness tests" |
| Publish a file that another process waits for in one step (write a temporary file, then rename). | A reader could read a process-number file between its creation and its write. | The same pull request, fourth commit |
| Give every wait an end. A clean-up sends the last signal before it waits, or waits with a deadline. | A clean-up waited for children after TERM with no deadline; a stopped child would have held the suite for the six hours of the gate limit. | The same pull request |
| Wait for an event, not for a time. A limit in real time is a guard against a hang, never the expected path. | Three tests with limits of 120 s, 10 s and an event limit failed on a loaded host and passed on the same code later. | #598 |
| Start few processes. Run a test in the process of the harness when it can. | One run of the supervisor's self-tests started 55,626 scripts in 783 seconds. On that macOS version each script start left 1 KiB in the kernel until the restart. | #600; #594 |
| Run for a change only the checks that depend on it. | Each gate of an application step ran 14 minutes of harness self-tests, because one check had the application and the harness as one source. | #594 |
| Key a cache of built dependencies by what the build consumes (the resolved graph of outside packages and their features), not by the form of the files that declare it. | The archives of compiled dependencies had the local manifests as their key. A step that added a crate, a feature table or a second declaration of a package that the build already had built every archive again: gates of 40 to 53 minutes against 15 to 17. Four repairs followed each other, each for one more form of manifest that the rule before it refused. | #630, #645, #674 (pull requests #722 and #725); `run.history` of the Studio lane, 2026-11-19 |

## Waiting and order

| A harness must | What happened | Evidence |
| --- | --- | --- |
| Give each piece of work an identity that other work can wait for. | A harness step had no card. Three lanes could only wait "120 minutes" for its merge, and waited long after it. | Decisions 84 and 85 on #331 and #594 |
| Let work on different files proceed at the same time, and order only the merges. | The rule "one shared step at a time" made six unrelated changes wait for each other. | AGENTS.md, Lanes; decision 85 |
| Know which work blocks the most other work, and give it the gate first. | The card that 56 cards wait for waited 97 minutes in one day behind the gates of other lanes. | #331; `run.history` of the Studio lane, 2026-11-18 |
| Let a lane work other cards while one step waits for a machine, and wake that step by the event, not by a timer. | A step needed a build of about two minutes on a host that one job of a Checks run held for 95 minutes. The lane held the step and did no other work. The build had passed 55 minutes after the first wait; a timed wait of 60 minutes kept the lane asleep for 35 minutes more. | #609; `run.history` of the Server lane, 2026-11-18 21:37 to 23:07 |
| Put a measurement in the queue of each shared resource that it takes, and let it hold the resource for one unit of work at a time. | A card of the owner asked for a measured cold gate. The measurement held the gate lock for 58 minutes and had no place in the order of the merges. The gate of the card that 50 cards wait for waited 53 minutes behind it, and a second lane waited behind that gate. | #630, the note of 2026-11-19; `run.history` of the Studio lane, 2026-11-18 23:59 |
| Record the time that work waits for a shared resource apart from the time that it runs. | The supervisor took the start time of a gate before the wait for the gate lock. For those 53 minutes the status of the lane said "full gate", and the history gives that gate 65 minutes. The owner's evidence for a card rested on such minutes; a separate measurement had to confirm them. | `architecture/run.sh`, `full_gate`; `run.history` of the Studio lane, 2026-11-19 01:04; #630 |
| Give each shared resource one queue, and serve it in the order of arrival. | The gates of one machine had two queues: the merge turn for a run, and the gate lock for every heavy command. The turn had no order: the waiter that tried first after a release took it. One request of the card that 50 cards wait for lost the turn to two runs that had asked 12 and 24 minutes later. Then a measurement, which had entered only the queue of the lock, took the lock for 26 minutes. That gate started 95 minutes after its request. A sentence for the leads after the first such measurement did not prevent the second. | #640; `run.history` of the Studio lane, 2026-11-19 02:27 to 04:53 |
| Take the cost of each job as an input of its queue. A job of one minute passes a job of forty minutes when the results of both stay valid in either order. | One lane waited 72 minutes in two hours for the merge turn. Its five gates took 7 minutes together and built nothing that the long gates built. Two hours later a gate of one minute waited 35 minutes behind a gate of 40 minutes. | `run.history` of the Nix lane, 2026-11-19 14:50 to 16:50, and of the Server lane, 17:51 to 18:27 |
| Release work from a blocker when the blocker's cause is gone, and make the next run the check. | That card stayed parked for 1 h 42 min on a card whose failures came from a machine without memory, after the machine had been restarted. | Decision 79 on #331 and #598 |
| Set no size or count limit without a measured reason. | A limit of 400 changed lines and the word "smallest" cut one plan into slices with a median of 188 lines; each slice paid one review and one full gate. | Decision 85; AGENTS.md, Steps |
| Bound how often an order of priority lets other work pass a waiter. | The merge turn gave precedence to the card that the most cards wait for, with no bound. One lane held a complete candidate and waited more than two hours in one evening while the gates of that card passed it again and again. The candidate was the repair of the gate time of that same card. | #640, step 4 (pull request #721); `run.history` of the Nix lane, 2026-11-19 |
| Keep a worker free for other work while its candidate waits for an exclusive resource. | A lane that asked for the gate did nothing until it had the merge turn. In 24 hours the three lanes waited 1,166 minutes for the turn, 27 percent of their time. One lane waited 173 minutes with a complete candidate, and the next repair that it owned could not start. | `run.history` of the three lanes, 2026-11-19 04:50 to 2026-11-20 04:50 |
| Measure how much of the time each exclusive resource is busy and how long each worker waits for it. When it is busy nearly all the time, it is the limit of the system, and each minute of a job there costs every worker. | The gate lock of the one build machine was busy for more than 20 of 24 hours. No measure showed that; the owner tuned sessions and cards. In that state a harness step with 30 minutes of self-tests held the lock while the card that 56 cards wait for needed it. | `run.history` of the three lanes, 2026-11-20; #640, step 4 (a gate of 38 minutes) |
| Let a dependency name the part of other work that it needs, not the whole item. Show a wait for a party outside the system that repeats. | A card could not finish: its last steps waited for a release of another repository, and a lane set it aside five times in 2.5 days. A second card needed only the merged part of it. That card and eight more behind it were not ready in that time, though the recorded answer of the product owner said not to wait. The measure showed the first card as ready, with a session on that day. | #63 and #60; decision 117 in the owner's record of 2026-11-20 |
| Read each finished part of a long qualification run when that part ends, and make the work item for a new failure then. Do not wait for the end of the run. | A nightly run of seven jobs was still in progress nine hours after its start. One job failed 6.6 hours after the start on a test that no card named. The leads read only a run that is complete, so no one read that failure for two hours, until a check of the owner. | Checks run 44652322249 of 2026-11-20; #753 |
| Refuse a dependency loop when a work item is written, and show each loop in every measure. | A foundation card named its consumers as dependencies, because its last step checks their use of it, and three consumers named the foundation. Nine cards, the whole cloud deployment chain, could not become ready. The lane parked the foundation card and worked other cards for seven days. No report showed the nine cards, because a card that is never ready is silent. A question of the project owner about accounts found it. | #241, #6, #8 and #242; the owner's record of 2026-11-20, decision 119 |
| Let several accepted changes share one run of an expensive gate: build one tree from the changes that wait, run the gate one time, and split the batch only when it fails. | Each small change paid a full gate under one lock. The lock was busy for 75 to 93 of every 120 minutes, and three lanes waited 25 to 100 lane-minutes in each window for the merge turn. | The owner's record of 2026-11-20 (checks of 08:58, 10:55 and 12:54); the design is that of merge queues with batches |
| Keep a dependency as a typed edge, answer "what is ready" with one query, and let a worker claim an item in one atomic act. | The run read each issue link in a section of the card text as a dependency. A sentence about consumers made the loop above; two cards that named each other were silent for ten hours on 2026-11-13. | #331 and #382; #241; the owner's record of 2026-11-13 and 2026-11-20 |

## State and configuration

| A harness must | What happened | Evidence |
| --- | --- | --- |
| Keep its state outside the supervisor process, as an explicit record of states and transitions. | A stop of a run lost its parked cards, its set-aside timers and its open gate request. | `architecture/run.sh`; the restarts of 2026-11-18 |
| Read its configuration between two sessions, not only at its start. | A new lead model needed a stop and a start of each run, at a moment between a gate and a session. | Decision 81 |
| Keep decisions, failures and their evidence where every machine reads them. | The owner's procedure, tools and decision log were files of one checkout on one Mac. | #603; this skill |
| Name every value of one machine as an argument: a path, a user, an account, a host. | The active GitHub account of the machine was the wrong one for the project. A landing script started itself again with a relative path and failed. | The owner's record of 2026-11-18 |
| Derive the state of a piece of work from its record. Keep no second copy of that state that a tool or a person must set. | A card had the board status "Merged" while it was open. The owner added a step to it, and no run could select the card until the owner set the status by hand. Another card kept the status "Blocked" for 36 hours after its last blocker had merged, and other cards waited for it. | #674, 2026-11-19 18:57; #15 and #672, the owner's record of 2026-11-19 12:00 |
| Deliver a change of a specification to the session that works on it, or hold the change until that session ends. | The owner changed the text of a step ten minutes into its session. The session completed its candidate with the first text two minutes later, and the change needed its own step, review and gate. The same had occurred that morning on another card. | #680, steps 1 and 1b; #640, step 1b; 2026-11-19 |
| Keep the record of each job, not only of the last one: what it built, and how long each part took. | The gate log held only the last gate. Twice in one day the owner needed what a completed gate had built, to judge a repair of the gate time, and the next gate had replaced the log. The second time, the registration times in the database of the build store gave the answer. | #674, the note of 2026-11-19 16:57 and the evidence of 18:55 |
| Mark finished work in the state that the reports of the tracker count, in the same act that marks it finished for the harness. | The harness marked a finished card in a field of the board, and the issue stayed open. The graph of the tracker counts closed issues: it showed 46 completed items while 107 cards were finished. The owner of the project read the graph and asked why the count of the harness was higher. The harness owner closed 42 issues by hand. | The owner's record of 2026-11-20 11:16 and the section after it; the Burn up graph of the project on that day |
| Report progress against the plan, and count the work items that the work itself made apart from it. | The measure counted every finished task card: 104 of 259. 66 of them were diagnosis, repair, review and harness cards that the work had made. Of the 166 cards of the product plan, 38 were finished. Three reports said 40 percent where the plan was at 23 percent. | The owner's record of 2026-11-20 11:16 |
| Keep the state of the harness as a graph of typed relations, built from its sources, and answer the questions of the owner from it. | On one day the owner made these queries by hand from card text, histories and git: the cards that an answer releases, a dependency loop, the order of a lane by what releases the most work, the merges between a good and a bad qualification run that touch a failing test, the records that settle a question. The first graph, made that afternoon, counted the cards that wait for a card through other cards: 84 for a card that the direct count did not name. It also showed that a planned second lane would collide with 19 changes of the running work. | The owner's record of 2026-11-20, decisions 117 to 121; the stack record |

## The machine

| A harness must | What happened | Evidence |
| --- | --- | --- |
| Record the health of each machine all the time (memory, the largest kernel zone, swap, disk, load) and set it beside every gate result. | Gates went from 23 to 105 minutes and one failed. The cause was found eleven hours after the first sign, because no record tied the gate times to the memory. | #600; #598 |
| Treat the health of the machine as evidence for a failure, not as its verdict: make one check that separates a failure of the machine from a defect of the step (the same step on the healthy machine), and keep the step's result open until then. | A lane wrote a diagnosis card for test failures of the hour without memory, and parked its main card on it. The same step passed its gate after the restart. | #598; decision 79 on #331 |
| Leave a shared workspace as the next job needs it. | A job left a folder that the next job could not remove; every later job failed at checkout. | #605 |
| Tell a failure of the machine's network from a failure of the work, and wait for the network without spending sessions and gates. | The network of the machine was gone for about 105 minutes. A gate failed after 15 minutes on a name that did not resolve, the next lead session ended after 20 seconds, and the supervisor wrote "GitHub could not be read" ten times. The step had no defect: its gate passed in the first try after the network came back. | #331, the note of 2026-11-18 19:53; `run.history` of the Studio lane, 18:04 to 20:29 |
| Keep the error text of every failed call to an outside service. | The supervisor discarded the error output of its backlog read. Its log could not say whether the account, the request limit or the network was the cause. | `architecture/run.sh`, the read of the board; the same incident |
| Confirm an act on an outside service by its effect, not by the answer to the call or by a status field. | GitHub answered a merge call with "502 Bad Gateway" and made the merge. The record of the pull request said open one hour later. The commit on the main branch had the tree of the gated head; that comparison was the proof. | #609; pull request #632 |
| Measure without disturbing. | A probe that started thousands of new files kept the scan service of the system busy for the lanes and could not rise above their background. A two-minute probe with existing files gave the answer. | #600 |
| Know each process that deletes from or writes to a store that the builds share, and run it under the lock of the builds. | The daemon of the package manager had its own automatic garbage collector, next to the clean-up of the harness, and no record listed it. Two of its rounds ran for 56 minutes inside one gate: checks with many small build steps took 4 to 8 times longer, and the gate lost about 45 minutes while two lanes waited behind it. A round starts when the daemon starts and when the free disk falls below a mark, and the builds themselves push the disk below that mark. | #720; the log of the daemon and the gate time record of 2026-11-20 |
| Record one trace for each step, with each agent session and each part of the gate as a span, with time, tokens and cost from every model vendor. | The session logs had no times. The owner wrote a recorder by hand to see the parts of a gate, and could not see what a step cost in tokens across two vendors. | The owner's record of 2026-11-20 (the gate time recorder); the stack record, Planned |

## Review

| A harness must | What happened | Evidence |
| --- | --- | --- |
| Give a reviewer the specification, the change, and the measured results as facts, failures included. | Two review rounds were rejected for defects that a cheaper adversarial read found before the third. | The review record of the pull request "Signal only own processes in the harness tests" |
| Prove a test in each environment that runs it. | A suite passed in two builds and had never run as the ordinary user, where its defect did harm. | The same pull request |
| Prove the repair of a cost on each kind of real work that paid it. | A card listed four slow gates as its evidence; two of them had added a crate. Its acceptance used one made change, an edit of an existing manifest, and that gate went from 58 to 26 minutes. The first real step after the repair added a crate. It built four of the five dependency archives again and its gate ran for 52 minutes, against 56 before the repair. | #630; #645; `run.history` of the Studio lane, 2026-11-19 04:53 |
| Give each open question a type, and send it to the role that owns that type. Only product, scope, stack, authority, a test oracle and an act that only the human can do reach the human. | In one afternoon the leads parked a card for Joel's answer three times. Two of the questions were choices of procedure: which evidence to capture, and what to do after three review rounds. Each park held its card until the owner answered and started the run again. Joel asked "why does it need me!". | #598 and #580; decisions 91 to 93 in the owner's record of 2026-11-18 |
| Wake the role that answers a question when the question is asked. The timer of that role is only the guard. | A lead parked the card that 50 cards wait for on two questions, one minute after a check of the owner. Accepted records held both answers. The owner looked every two hours and answered 95 minutes later; a second card waited 76 minutes in the same way. The lane worked other cards in that time, and its main card did not move. | #331, the note of 2026-11-19 08:53; #651; `run.history` of the Studio lane, 2026-11-19 07:18 |
| Record why work stopped as a field with fixed values: a question for a role, a wait for other work, a deferral. | The watcher that wakes the owner looked for a name in the free text of a park line. A lead parked a card that other cards wait for with a text that did not have the name, and the watcher did not wake. The timed check came one minute later by chance. | #15; `run.history` of the Server lane, 2026-11-19 14:49 |
| Before a question about authority gets an answer, ask the product owner, in the words of the product, whether the product needs the operation at all. The options of the session that asks are not the whole choice. | A lead asked which credential an operator workflow needs. The delegate of the product owner chose one of the two options, and then a third option. Both were wrong: the product has no operator step. One card got three texts in two hours, and three accepted records said the old rule. | #15, the notes of 2026-11-19 14:53 to 16:41; pull request #701 |
| Have a second route for work that a model provider refuses, and record the refusal as a result. | The provider's content filter stopped a fresh diagnosis session about a crash of a shell. The owner finished the diagnosis from the crash reports of the system. | #598; the pull request "Update the working rules and repair the harness process test" (#610) |
| Correct a wrong statement where it was made. | The owner named a cause for slow tests that the next measurement refuted (16 of 783 seconds). | #594, the correction comment |
| Read the answer that a change gives to a question of its specification as a finding with an owner. | A specification asked a change to confirm a property or to name the case that breaks it. The pull request named the case: the order can pass one waiter without end. Nobody owned that sentence. Eleven hours later that case cost a lane two hours. | Pull request #663; #640, step 4 |
| Give a decision to a worker as the exact condition, with its source quoted. A paraphrase makes a second rule. | The owner answered the question of a lead with "keep the behaviour of the main branch" and added a limit in other words, taken from a comment in the code. The condition in the code was wider than the comment. The lead built the narrower rule, the review rejected it for the conflict, and the card parked a second time: one session of 26 minutes and one review round. | #331, decisions 113 and 114 in the owner's record of 2026-11-19 |
| Put a question for the owner of the project as one sentence that takes one word as its answer, with the recommended choice, the smallest choice and what the answer releases. | Two questions waited 7.5 and 4 hours as items in reports, with tables of alternatives in words of the mechanism. They held 13 of the 26 open plan cards of one lane. Asked again as two plain sentences, both were answered in one minute. | #73 and #60; the owner's record of 2026-11-20 12:02 |
| Write the decisions of the owner as principles where every worker reads them. | The owner of the project gave the same kind of answer four times in two days: by hand at the pilot, no act for each machine, the smallest thing that is correct. The answers were in the notes of one session, so each lead asked again and waited. | #15, #324, #73 and #60; `docs/arch/principles.md` |
| Review the design of a work item before its first code, with the strongest model. | A lead planned the steps and wrote the code, and the reviewer saw the design only one step at a time, in the change of that step. One application then needed a refactor of 82 merged changes, and 99 open cards waited behind it. | #331; the owner's record of 2026-11-20 13:11 |
| Measure the honesty of the tests and the rework of merged code, not only that the gate passes. Make a removed or changed assertion visible at the push, with its reason. | The harness reported merged steps and closed cards as its progress. The first measure of the tests found 41 and 195 removed assertions in the last 300 commits of two applications, tests with no assertion, and that only 50 and 35 percent of the lines that those applications got in ten days were still in the code ten days later. No report had held one of these numbers. | `architecture/quality/facts.sh` and its output of 2026-11-20; the pull request that added this row |
| Keep everything that a new session needs in the repository: the tools, the definition of the supervising agent, its procedure and its open work. A folder that the version control ignores holds only what can be made again, and it is outside the checkout. | The supervisor of the lanes kept its tools, its check procedure, the specifications of its steps and its record in an ignored folder of one checkout for six days. A clone had none of it, a clean of the checkout would have removed it, and a new session could not continue. The ignored folders of the lanes also filled the disk: 23 GiB, a third of it from finished work, on a disk with 20 GiB free. | The pull request that added this row; `references/open.md` |
| Run the tests of the harness with exactly the programs of the gate's check before a harness step takes the merge turn. | A step passed each of its tests on the machine and failed the gate two times in the build of the harness tests: a rule of the harness rejected two new lines, and a tool called a program that the build does not have. The two failed gates held the merge turn of the lanes for 28 minutes. | The pull request that added this row |
